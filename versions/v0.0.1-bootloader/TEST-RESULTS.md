# v0.0.1-bootloader — 测试记录（项目起点）

## 这一版是什么

**GitHub 仓库 `Holmes-2011/The-Develop-of-zeroOS` 在本次推送之前的状态**，
也就是这个项目最原始的样子：只有一个引导层，还没有配套的新内核。

| 文件 | 大小 | 来源 |
|---|---|---|
| `boot.asm` | 3298 | GitHub 上的 `zeroOs 引导层.asm`（原文件名带空格和中文，这里改名以便统一） |
| `kernel.c` | 1259 | 借用 `v0.1-hello/kernel.c`（444 字节，装得下它 20 扇区的限制） |

> 这一版**没有 `entry.asm` / `link.ld`**（上游当时也没发过），
> 测试时用的是工程里的共享文件，见下文对照实验。

## 和后来版本的关键差异

| 项目 | v0.0.1（本版） | 当前 v0.5.1 |
|---|---|---|
| `KERNEL_SECTORS` | **20**（10 KB） | 40（20 KB） |
| 进保护模式前有没有 `cli` | **没有** ❌ | 有 ✅ |
| 镜像是否补零到 512 KB | 否 | 是 ✅ |
| 有没有 IDT / PIC | 无 | 有 |

`boot.asm` 的关键位置：

```
14:    cli                       ; ← 只在初始化阶段关中断
20:    sti                       ; ← 之后一直开着
33:    lgdt [gdt_descriptor]
35:    mov eax, cr0               ; ← 33 和 35 之间没有 cli，中断是开的
37:    mov cr0, eax
```

**缺陷**：`lgdt` 只设了段表（GDT），**没有 `lidt`（IDT）**。
此时 IDT 寄存器里还是实模式的中断向量表（基址 0，长度 0x3FF），
保护模式会拿"描述符"的格式去解析它 —— 全是垃圾。
第一个时钟中断（IRQ0）一到 → 取不到合法中断门 → **三重故障 → 整机重启**，无限循环。

## 对照实验：三重故障到底由哪一处 `cli` 消除

这个缺陷有**两个**都可以堵住它的位置：引导层（进保护模式前）和入口垫片（内核第一条指令）。
为了搞清楚它们各自的作用，做了 2×2 对照 —— **内核完全相同，只换这两处**。

**检测方法**：启动 1.5 秒后，每 100ms 读一次 CPU 的 `EIP`，共 25 次。

- **稳定**：`EIP` 始终停在同一个内核地址（`kmain` 的 hlt 循环里）
- **重启循环**：`EIP` 在各个 BIOS 地址间乱跳

| 组合 | 引导层 | 入口垫片 | 采样到的 EIP 种类 | EIP 落在内核区的比例 | 判定 |
|---|---|---|---|---|---|
| **A** | 原版（无 `cli`） | 原版（无 `cli`） | **10 种** | **33%** | ❌ **在重启** |
| **B** | 原版（无 `cli`） | 已修（有 `cli`） | 1 种 | 100% | ✅ 稳定 |
| **C** | 已修（有 `cli`） | 原版（无 `cli`） | 1 种 | 100% | ✅ 稳定 |
| **D** | 已修（有 `cli`） | 已修（有 `cli`） | 1 种 | 100% | ✅ 稳定 |

### 结论

1. **原始状态（A）确实会崩** —— `EIP` 在 10 个不同地址之间跳，只有 33% 的时间在内核里，
   这就是三重故障重启循环的铁证
2. **两处 `cli` 任选其一就够了**（B 和 C 都稳定）—— 它们是**冗余的两种修法**，不是必须都有
3. 所以工程里保留两处**是刻意的双保险**，不是重复代码

### 一个测试方法上的教训

第一次做对照时只换了引导层、没换入口垫片 —— 那测的其实是 **B（已经修好的组合）**，
所以两组都 10/10 通过，看起来像"这个缺陷复现不出来"。

**只隔离一个变量是不够的，要隔离到能区分出差异为止。**
