## 项目决定（2026-10-11，v0.12 调整）

目标是一个**能深入系统内部**的 Agent：普通电脑上的 AI 助手只是一个普通程序，被沙箱和权限挡在外面，
看不到内核里发生了什么；zeroOS 的内核是自己写的，可以从一开始就把"让 Agent 看清系统"设计进去。
因此分三层，**先做 ① 和 ②**，③ 以后再定：

| 层 | 内容 | 在哪 |
|---|---|---|
| ① 感知 + 工具 | 内核各子系统把自己的状态报出来（计数器、采样、事件）；Agent 能调用的诊断工具、权限等级、审计日志 | 内核，**本仓库** |
| ② 系统直觉 | 项目自己的小模型：一直开着，持续读感知层的采样，判断系统是否出现异常（内存泄漏、中断风暴……） | **单独构建，不在本仓库**，跑在宿主机上（以后搬进用户态）；内核只提供采样流和 `verdict` / `get_intuition` 接口 |
| ③ 推理和对话 | 理解用户的话、规划排查步骤、解释原因 | 以后再定（下面"实测约束"里的 1B ~ 3B 估算属于这一层） |

## 一、它是什么

**系统内置 Agent**：zeroOS 自带的一个系统服务。用户用自然语言提要求
（"看看哪个程序占内存最多""帮我把这个设置改回默认"），Agent 理解意图后，
**通过系统提供的、受权限控制的"工具"** 去查询状态、执行操作，并把结果告诉用户。

它不是一个普通应用，区别在于：

| | 普通 AI 应用 | zeroOS 内置 Agent |
|---|---|---|
| 能做什么 | 只能做该应用自己能做的事 | 能调用系统级工具（进程、设置、文件、设备） |
| 权限从哪来 | 应用自己的权限 | **和用户走同一套权限系统**，不多一分 |
| 用户怎么确认 | 各家自己实现 | 系统统一的确认界面，Agent 无法伪造 |
| 谁能审计 | 看应用 | 系统统一记录每一次工具调用 |

## 二、核心设计判断

### 1. 模型在本机运行，分层而不是混成一团

```
┌──────────────────────────────────────────┐
│  模型：权重 + 推理引擎（矩阵运算、注意力……）       │  ← 可替换：换模型只换权重和结构描述
├──────────────────────────────────────────┤
│  Agent 循环                                │  ← 对话、把工具清单交给模型、
│    模型输出"要调用哪个工具、什么参数"，           │     解析模型输出、调用工具、把结果交回模型
│    循环把结果交回模型……直到完成                 │
├──────────────────────────────────────────┤
│  工具接口 + 权限检查 + 确认框 + 审计日志          │  ← zeroOS 自己的、长期稳定的部分
└──────────────────────────────────────────┘
```

**只有最下面一层在内核里**（2026-10-18 的决定）。上面两层先跑在宿主机上，通过串口协议调用最下面一层；
以后搬进 zeroOS 用户态时，只是把串口换成系统调用，消息、权限判定、确认框、审计全部不变。
不管模型在哪里运行，它都只能通过 `tools_invoke()` 做事；确认框由内核绘制、只认物理键盘，模型画不出"已同意"。

**为什么最终要移出内核**：模型的输出天生不可信——它读到的文件、网页里藏的文字可以操纵它
（提示词注入）。在内核里，"权限检查"只是它自愿遵守的约定；到了用户态，才由硬件强制执行。
另外推理代码量大、出错概率高，在用户态出错只是这个程序崩掉，不会整机崩溃。

### 实测约束（v0.10 的 `bench`）

| 约束 | 数字 | 影响 |
|---|---|---|
| 内存 | 32 位，只用 3GB 以下 | 3B 模型必须 **4 位量化**（约 1.5GB）；1B 可以 8 位（约 1GB）。更大的模型要先升级到 64 位 |
| 速度（QEMU，Apple Silicon Mac 上软件模拟 x86） | 约 6 千万次乘加 / 秒 | **1B ≈ 15 秒 / 词，3B ≈ 47 秒 / 词**。真机快很多倍，但仍是单核 |
| 权重读取 | GB 级 | 装不进启动镜像，需要硬盘驱动从第二块磁盘读 |

### 2. 权限和"默认锁定 + 开发者模式"保持一致

《设计讨论纪要》定下的原则是**默认偏安全锁定，开发者模式解锁**。Agent 沿用同一套，
每个工具标一个权限等级：

| 等级 | 例子 | 默认模式 | 开发者模式 |
|---|---|---|---|
| **只读** | 查运行时间、内存占用、进程列表 | 直接执行 | 直接执行 |
| **可撤销** | 改音量、改用户级设置 | 执行，可一键撤销 | 直接执行 |
| **破坏性** | 删除文件、结束进程 | **每次都要用户确认** | 每次都要用户确认 |
| **系统级** | 改系统设置、装驱动、改引导项 | **不允许** | 每次都要用户确认 |

两条硬规则：

- **Agent 永远不能比用户本人权限更大。** 用户自己做不了的事，Agent 也做不了。
- **确认界面由内核绘制**，Agent 只能"申请确认"，不能自己画一个"已同意"。
  这是防"提示词注入"的关键：网页、文件里藏的恶意文字可以骗模型去调用工具，
  但骗不过一个只听物理键盘的确认框。

### 3. 推理引擎做成"积木"，适配自己设计的结构

模型结构是项目自己设计的，所以推理引擎不写死某一种开源结构，而是提供通用的积木：
矩阵 × 向量（f32 / 8 位 / 4 位量化）、归一化（RMSNorm / LayerNorm）、注意力（含 KV 缓存）、
激活函数（SiLU / GELU 等）、位置编码（RoPE 等）、softmax 和采样。

先用一个公开的超小模型（Llama 类结构，几十万参数）把整条链路验证通——输入一句话，屏幕上逐字生成。
项目模型训练好后，按它的结构说明把积木拼起来、换上权重。

**需要模型方提供**：层的类型和顺序、各维度、归一化和激活函数的种类、位置编码方式、
分词器（词表 + 规则）、权重的保存格式和量化方式。

## 三、工具协议（草案）

每个工具在内核里登记一条描述：

```c
struct agent_tool {
    const char *name;          /* "get_uptime" */
    const char *description;   /* 给模型看的说明 */
    const char *params_schema; /* 参数的 JSON Schema */
    int         level;         /* 只读 / 可撤销 / 破坏性 / 系统级 */
    int       (*handler)(const char *args_json, char *out, int out_size);
};
```

模型调用工具的格式（模型输出里的一段结构化文本，具体格式随项目模型的训练方式定），例如：

```
<tool>{"name":"get_uptime","args":{}}</tool>
```

Agent 循环解析出来，交给工具接口；工具接口按权限等级决定直接执行、弹确认框还是拒绝，
把结果（或 `denied_by_user`）作为下一轮的输入交回模型。

每一次调用（无论成功、被拒绝还是需要确认）都写进审计日志：时间、工具名、参数、权限等级、结果。

## 五、路线图

每一步都是一个独立可测的版本，沿用现有的"一版一个目录 + TEST-RESULTS.md"做法，测试通过再发布。

| 阶段 | 版本（暂定） | 内容 | 对 Agent 的意义 |
|---|---|---|---|
| 地基 | **v0.6.1** ✅ | 内存上限检查、`.bss` 清零、可移植构建、自动测试 | 后面每一步都能放心加代码 |
| 输入 | **v0.7** ✅ | IRQ1 键盘驱动 + 扫描码转字符 + 行缓冲 | 确认框的物理输入来源 |
| 终端 | **v0.8** ✅ | 屏幕文字输出 + 内核 shell | shell 的命令表就是**第一版工具登记表** |
| 内存 | **v0.9** ✅ | 内核搬到 1MB 以上；物理页分配；分页；内核堆 | 能放下权重和 KV 缓存 |
| 浮点 | **v0.10** ✅ | FPU / SSE2、数学函数、`bench` 实测速度 | 推理的运算基础；量出模型规模的现实约束 |
| 磁盘 | **v0.11** ✅ | 块设备接口 + ATA PIO 驱动（QEMU 里约 7–8 MB/s，3GB 约 7 分钟）；AHCI / NVMe 以后挂在同一接口下 | 加载 GB 级权重 |
| **感知层** | **v0.12** ✅ | 各子系统计数器；时钟中断里每 100 毫秒采样一次；事件日志；按需分页区（缺页可观测、不再停机）；`metrics` / `events` / `telstream` | **Agent 第一次看得见系统内部** |
| 工具层 | **v0.13** ✅ | 工具登记 + 4 级权限 + 开发者模式 + 内核绘制的确认框（丢弃提前敲好的按键、20 秒超时）+ 审计日志；`heap_check` / `pmm_check` 诊断；`inject_fault` 故障注入（仅开发者模式）。人用的 `tool` 命令和 Agent 走同一个入口 | Agent 能查、能测；能制造故障来训练和验证系统直觉 |
| 桥接协议（内核侧） | **v0.14** ✅ | 串口接收（IRQ4）+ JSON Lines 协议 + 事件推送 + `verdict` 接收 + `get_intuition` 工具（见 `agent-bridge-protocol.md`）；`bridge_test.py` 35 步协议测试 | **宿主机上的 Agent 第一次能操作 zeroOS**；直觉模块通过采样流常驻 |
| 高半内核 | v0.15 | 内核搬到虚拟地址 3GB 以上（物理内存映射到 0xC0000000 起，堆 / 按需分页区挪到 0xF0000000 后），0 ~ 3GB 留给用户态；行为对用户不变 | 用户态的前提：现在恒等映射把低地址全占了 |
| 用户态 | v0.16 | ring 3 段 + TSS + `int 0x80` 系统调用（exit / write / getkey / uptime / tool / sleep）；内核内嵌一个测试程序，`run` 命令跑它；用户态的缺页 / 非法指令杀掉程序回到 shell，而不是停机 | 第一个 ring 3 程序；工具调用从用户态走同一个入口 |
| 任务切换 | v0.17 | 调度器、抢占、浮点上下文（FXSAVE） | 命令行和程序同时跑 |
| Agent 搬进 zeroOS（阶段 A） | 之后 | 协议从串口换成系统调用；模型推理（积木式引擎）在用户态运行 | 不再依赖宿主机 |
| 64 位 | 之后 | 长模式、更大地址空间 | 3B 以上的模型 |

## 六、待定问题

1. **第 ③ 层的模型**：结构说明和权重格式，做推理引擎之前需要。
2. **量化方式**：3B 必须 4 位；是训练后量化，还是训练时就考虑量化（效果更好）？
3. **工具调用格式**：模型输出里用什么格式表示"调用某个工具"，取决于模型怎么训练。
4. **开发者模式的开启方式**：要不要像手机一样需要重启 + 物理按键确认，防止被远程开启？
5. **Agent 能不能调用 Agent**：多步任务、后台任务要不要支持，怎么限额？
