# zeroOS 系统内置 Agent —— 设计与路线图

> 状态：**设计草案**（v0.6.1 时撰写）。本文只定方向和顺序，不含实现代码。
> 内核目前只有：引导、IDT、PIC、100 Hz 时钟。离"系统内置 Agent"还有很长的路，
> 这份文档的作用是让每一步都朝这个方向走，而不是走到一半发现地基不对。

---

## 一、它是什么

**系统内置 Agent**：zeroOS 自带的一个系统服务。用户用自然语言提要求
（"看看哪个程序占内存最多""帮我把这个设置改回默认"），Agent 理解意图后，
**通过系统提供的、受权限控制的"工具"** 去查询状态、执行操作，并把结果告诉用户。

它不是一个普通应用，区别在于：

| | 普通 AI 应用 | zeroOS 内置 Agent |
|---|---|---|
| 能做什么 | 只能做该应用自己能做的事 | 能调用系统级工具（进程、设置、文件、设备） |
| 权限从哪来 | 应用自己的权限 | **和用户走同一套权限系统**，不多一分 |
| 用户怎么确认 | 各家自己实现 | 系统统一的确认界面，Agent 无法伪造 |
| 谁能审计 | 看应用 | 系统统一记录每一次工具调用 |

## 二、三条核心设计判断

### 1. 模型不放进内核

大模型推理需要几 GB 内存和 GPU/NPU 加速，放在内核里既做不到也不应该做。
Agent 分成三层，**只有最下面一层在内核里**：

```
┌──────────────────────────────────────────┐
│  模型后端（远程 API 或 本地模型）              │  ← 可替换
├──────────────────────────────────────────┤
│  Agent 服务（用户态）                        │  ← 对话循环、调用工具、展示结果
│    把用户请求 + 工具清单发给模型，                │
│    模型返回"要调用哪个工具、什么参数"，            │
│    服务去调用，把结果再交给模型……直到完成           │
├──────────────────────────────────────────┤
│  工具接口 + 权限检查 + 审计日志（内核）          │  ← zeroOS 自己的、长期稳定的部分
└──────────────────────────────────────────┘
```

**最需要先设计好、最该长期稳定的是最下面一层。** 模型会换代、后端会从远程换成本地，
但"系统暴露哪些工具、每个工具要什么权限、调用怎么记录"是 zeroOS 自己的东西。

### 2. 权限和"默认锁定 + 开发者模式"保持一致

《设计讨论纪要》定下的原则是**默认偏安全锁定，开发者模式解锁**。Agent 沿用同一套，
每个工具标一个权限等级：

| 等级 | 例子 | 默认模式 | 开发者模式 |
|---|---|---|---|
| **只读** | 查运行时间、内存占用、进程列表 | 直接执行 | 直接执行 |
| **可撤销** | 改音量、改用户级设置 | 执行，可一键撤销 | 直接执行 |
| **破坏性** | 删除文件、结束进程 | **每次都要用户确认** | 每次都要用户确认 |
| **系统级** | 改系统设置、装驱动、改引导项 | **不允许** | 每次都要用户确认 |

两条硬规则：

- **Agent 永远不能比用户本人权限更大。** 用户自己做不了的事，Agent 也做不了。
- **确认界面由内核绘制**，Agent 只能"申请确认"，不能自己画一个"已同意"。
  这是防"提示词注入"的关键：网页、文件里藏的恶意文字可以骗模型去调用工具，
  但骗不过一个只听物理键盘的确认框。

### 3. 先用"桥接"跑通，再把网络搬进系统

调用远程模型需要：网卡驱动 → TCP/IP → DNS → TLS（HTTPS）。这是整条路线里最重的一块。
如果等它全部做完才开始做 Agent，工具接口和权限模型就要很久以后才能被真正用起来检验。

所以分两步：

1. **桥接阶段**：zeroOS 通过串口把"工具清单 / 工具调用 / 结果"发给宿主机（Mac），
   宿主机上一个小程序负责调用模型 API。**工具接口、权限检查、确认框、审计日志全部在 zeroOS 里**，
   宿主机只当"网线"。
2. **原生阶段**：zeroOS 有了自己的网络协议栈后，把"网线"换成真正的 HTTPS，
   上面的工具接口一行不用改。

## 三、工具协议（草案）

每个工具在内核里登记一条描述：

```c
struct agent_tool {
    const char *name;          /* "get_uptime" */
    const char *description;   /* 给模型看的说明 */
    const char *params_schema; /* 参数的 JSON Schema */
    int         level;         /* 只读 / 可撤销 / 破坏性 / 系统级 */
    int       (*handler)(const char *args_json, char *out, int out_size);
};
```

桥接阶段的串口协议用"一行一个 JSON"（JSON Lines），方便两边解析和调试：

```
zeroOS → 宿主机   {"type":"tools","tools":[{"name":"get_uptime","description":"...","params":{}}]}
宿主机 → zeroOS   {"type":"call","id":1,"name":"get_uptime","args":{}}
zeroOS → 宿主机   {"type":"result","id":1,"ok":true,"output":"uptime 42 s"}
zeroOS → 宿主机   {"type":"result","id":2,"ok":false,"error":"denied_by_user"}
```

每一次调用（无论成功、被拒绝还是需要确认）都写进审计日志：时间、工具名、参数、权限等级、结果。

## 四、还缺什么（前置依赖）

| 能力 | 现在 | Agent 为什么需要它 |
|---|---|---|
| 时钟中断 | ✅ v0.6 | 超时、计时、以后的调度 |
| 键盘输入 | ❌ | 用户输入请求；**确认框只认物理键盘** |
| 终端 / 内核 shell | ❌ | 第一批工具就是 shell 命令；显示 Agent 的回复 |
| 内存管理（物理页 + 分页 + 堆） | ❌ | JSON 解析、对话历史都需要动态内存 |
| 内核搬到 1MB 以上 | ❌ | 现在内核被限制在 `0x1000 ~ 0x7C00`（约 27KB），放不下 |
| 用户态 + 系统调用 | ❌ | Agent 服务要跑在用户态，和内核隔离 |
| 进程 / 调度 | ❌ | Agent 服务和其他程序同时运行 |
| 存储 + 文件系统 | ❌ | 审计日志落盘、文件类工具 |
| 网卡驱动 + TCP/IP + DNS + TLS | ❌ | 原生阶段直连模型 API |
| 安全的密钥存储 | ❌ | 存 API 密钥 |

## 五、路线图

每一步都是一个独立可测的版本，沿用现有的"一版一个目录 + TEST-RESULTS.md"做法。

| 阶段 | 版本（暂定） | 内容 | 对 Agent 的意义 |
|---|---|---|---|
| 地基 | **v0.6.1** ✅ | 内存上限检查、`.bss` 清零、可移植构建、自动测试 | 后面每一步都能放心加代码 |
| 输入 | v0.7 | IRQ1 键盘驱动 + 扫描码转字符 + 行缓冲 | 确认框的物理输入来源 |
| 终端 | v0.8 | 屏幕文字输出 + 内核 shell（`help` / `uptime` / `mem`） | shell 的命令表就是**第一版工具登记表** |
| 内存 | v0.9 | 内核搬到 1MB 以上；物理页分配；分页；内核堆 `kmalloc` | 解除 27KB 限制；能做 JSON |
| **Agent 原型** | v0.10 | 工具登记 + 权限等级 + 确认框 + 审计日志；串口 JSON Lines 协议；宿主机桥接程序 | **Agent 第一次真正可用**：在 zeroOS 里用自然语言查询系统状态 |
| 隔离 | v0.11+ | 用户态（ring 3）、TSS、系统调用、进程 | Agent 服务移出内核 |
| 存储 | 之后 | 磁盘驱动 + 简单文件系统 | 审计日志落盘、文件类工具 |
| 联网 | 之后 | virtio-net / e1000 驱动；移植成熟的 TCP/IP 栈和 TLS 库 | 去掉桥接，zeroOS 直连模型 API |
| 本地模型 | 远期 | 大内存、GPU/NPU 驱动 | 断网可用、隐私更好 |

网络协议栈和 TLS **不建议自己从零写**：可以移植 lwIP（TCP/IP）和 BearSSL / Mbed TLS（TLS）
这类专为嵌入式设计、许可证兼容 Apache-2.0 的成熟库。这和"基于成熟开源组件二次设计"的总体路线一致。

## 六、待定问题

1. **模型后端选谁**：远程 API（效果好、需要联网和密钥）还是本地模型（隐私好、硬件要求高）？
   建议原型阶段用远程 API，工具协议保持和具体厂商无关。
2. **API 密钥存哪**：桥接阶段放在宿主机上；原生阶段需要系统级的安全存储。
3. **隐私**：哪些系统信息允许发给远程模型？是否需要"本次对话发送了哪些数据"的可见记录？
4. **开发者模式的开启方式**：要不要像手机一样需要重启 + 物理按键确认，防止被远程开启？
5. **Agent 能不能调用 Agent**：多步任务、后台任务要不要支持，怎么限额？
